# DSH 接入检查

检查对象：设备 `ssh dsha` 上的 `/root/dsh-moss-live`，Git 基线 `dc27cdd`；DSH `0.2.2-rc.1`。Windows 工作目录的六个 `lib/*.js` 文件与设备端 SHA-256 一致。

## 结论

原实现使用了 DSH 的包发现和路由入口，但前端通过手工 DOM 操作绕开槽位渲染，宿主绕开 Connection 鉴权，语音播放确认存在协议偏差。依据用户要求重做。产品保持独立 MOSS 语音 Chat，DSH 提供宿主能力。

## 已确认的问题

| 问题 | 证据与影响 | 重做要求 |
| --- | --- | --- |
| 自定义接口未使用 DSH 登录鉴权 | `lib/host.js` 只比较 Origin/Host；新增回归用例中，无登录请求返回 200，预期 401 | HTTP 与 WebSocket 升级均调用 `connection.requestRejection(request)`；声明服务依赖 |
| 入口绕开 React 槽位 | `Entry` 返回 null，另用中文“更多”查找节点、MutationObserver 插入原生按钮 | 注册真实 React 组件，使用 owner 提供的 `wide`，不接管宿主 DOM |
| 面板没有挂载 | `installOverlay()` 创建 ref，却没有把 ref 交给容器；effect 因 `ref.current === null` 返回 | 面板直接由 React 在 `shell.overlay` 渲染 |
| 插件卸载不完整 | 保存了 `overlayStop`，`teardown()` 未调用；模块级 state 和异步启动容易跨激活周期残留 | 每次 apply 创建独立控制器；由 Cordis effect 和槽位生命周期释放资源 |
| 浏览器依赖图不完整 | `package.json` 的 `dsh.client.inject` 为空 | 声明 renderer、layout、sidebar 等槽位所有者的包依赖；与导出的服务 `inject` 区分 |
| 配置缺少框架 schema | 没有导出 `Config`，模型、音色和指令未获得 DSH 配置校验 | 使用官方 Schemastery Config；密钥使用凭据引用 |
| 打断进度计算错误 | `actualPlayedMs()` 从整轮开始计时，包含已确认片段和排程等待 | 仅计算当前未完成队首片段实际播放时长；先确认已经播完的片段 |
| 媒体生命周期易竞态 | 麦克风授权、读取配置和音频 resume 等异步操作只依赖共享 active 标志 | 启动代次失效检查；过期操作返回的 stream 立即停止 |
| 代理缓冲无上限 | 上游连接前 pending 数组无限增长，发送不检查拥塞 | 限制消息大小、待连接队列及发送积压；卸载主动终止两端 |
| 留有临时诊断代码 | `/dsh-moss-live/diag` 接收请求并写固定 `/tmp/moss-diag.json` | 删除诊断接口和布局上报 |
